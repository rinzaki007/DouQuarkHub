# MovieSync 代码审查报告

## 结论

原版已经具备完整业务闭环，但代码明显处于“功能优先、架构后补”的阶段。主要问题不是某一两个函数写得不好，而是**边界不清、运行态数据管理分散、第三方接口处理不统一、后台任务生命周期不严谨**。

本次 2.0 重构保留原功能和页面交互，同时把核心实现拆成 Web / Service / Client / Storage 层。

## 🔴 高优先级问题

### 1. Docker 数据持久化不完整

原版 `auth.json` 和 `config.json` 在项目工作目录，而 Docker Compose 只挂载 `/app/data`。容器重建后管理员认证和主要配置可能丢失。

**2.0：** 所有运行态数据统一进入 `data/`，Docker 只需要挂载一个 volume。

### 2. Cookie 被同步到浏览器 localStorage

夸克 Cookie 是高敏感凭据。原版服务端保存一份、浏览器又保存一份，并在多个 API 中再次上传。

**2.0：** Cookie 只保存在服务端；公共配置 API 不返回真实 Cookie；搜索、转存、追剧都由服务器直接读取。

### 3. 图片代理存在 SSRF 风险

原版 `/api/proxy-img?url=` 没有限制目标 URL，服务器会直接请求用户提供的地址。

**2.0：** 仅允许 HTTPS，并限定为 `doubanio.com` 图片域名。

### 4. 转存接口信任客户端候选 Token/FID

原版浏览器直接携带 `stoken` 和文件 FID 发给服务端。即便当前接口只对管理员开放，也不应该把第三方访问凭据当作客户端可信数据。

**2.0：** 搜索结果不再向浏览器返回 `stoken`；转存时服务器重新获取分享 Token，并验证所选 FID 属于该分享。

### 5. 自动追剧实际忽略任务自己的 interval_hours

原版调度器固定每小时执行一次，不论任务设置 3、6、9 还是 12 小时。

**2.0：** 每条订阅记录 `next_run_at`，真正按照自己的周期运行。

## 🟠 中高优先级问题

### 6. 后台任务缺少执行互斥

手动点击“立即运行”和后台自动巡检可以同时针对同一个订阅执行，存在重复转存和 JSON 并发写入的风险。

**2.0：** 增加 running set + RLock。

### 7. JSON 文件直接覆盖写

原版写 JSON 过程中进程崩溃时可能留下损坏文件。

**2.0：** 临时文件 + fsync + os.replace。

### 8. 第三方 HTTP 调用分散

原版 requests 调用分布在多个文件，超时、错误处理、Session 复用和重试策略不统一。

**2.0：** 增加 HttpClient，并为线程场景使用 thread-local Session。

### 9. Telegram 页面用正则抽 HTML

HTML DOM 结构稍有变化就可能误解析。链接也可能被嵌套标签影响。

**2.0：** BeautifulSoup 解析消息节点和链接。

### 10. 大量异常被静默吞掉

原版大量 `except Exception: pass`，线上出现问题时无法回答“究竟哪里坏了”。

**2.0：** 关键路径统一日志、用户可见错误和内部异常记录。

## 🟡 中优先级问题

### 11. 资源目录只检查前 200 项

同名目录或者分享资源超过一页时可能漏掉。

**2.0：** 增加分页和扫描上限。

### 12. episode 正则存在字符类写法问题

原版类似 `[E|e]`、`[集|话|期]` 会把 `|` 当普通字符，而不是“或”。

**2.0：** 使用 `re.IGNORECASE` 和真正的字符集合。

### 13. `/openlist` 前端链接缺少后端路由

页面有入口，但原版 Flask 没有 `/openlist` 路由。

**2.0：** 增加配置驱动重定向。

### 14. 前端内联 JSON 事件处理存在注入/转义隐患

候选对象直接 `JSON.stringify()` 嵌进内联 onclick，在字符串包含特殊字符时容易产生语法问题甚至 XSS。

**2.0：** 改为索引状态引用。

### 15. 后台存在未使用的重复 admin.js

后台页面实际使用自身的内联脚本，`static/js/admin.js` 是一份重复实现。

**2.0：** 删除冗余脚本，后台逻辑只保留一份。

## 🟢 保留的合理设计

- Flask 对这个规模的个人自托管工具仍然足够。
- JSON 存储在单实例低并发环境下可以接受，因此本次没有为了“看起来专业”强行引入数据库。
- 单 worker + threads 适合内部调度与当前体量，避免多 worker 导致调度器重复启动。
- 顶层兼容模块保留，降低已有部署和外部脚本的升级成本。
